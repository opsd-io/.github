# Contributing to OPSd

This is the shared contribution procedure for the public OPSd repositories.
Each repository may add project-specific checks, but the rules below apply
across the organization.

## Pull Requests And Commits

Every pull request title and every commit included in it must use:

~~~text
type(scope): short imperative description
~~~

The type must be one of:

- feat — a user-visible feature;
- fix — a bug fix;
- perf — a performance improvement;
- docs — documentation only;
- test — tests only;
- ci — CI or workflow changes;
- build — build or packaging changes;
- chore — maintenance;
- refactor — an internal code change;
- deps — dependency changes;
- revert — reverting an earlier change.

The scope is required and must describe the affected area. Typical scopes
include cli, modules, tests, asdf, workflows, ci, docs, and release. Use the
scope allowed by the target repository's validation workflow.

Examples:

~~~text
feat(cli): add manifest validation
fix(modules): correct managed database defaults
ci(workflows): pin checkout action
docs(docs): document contribution checks
~~~

Breaking changes may use the ! marker:

~~~text
feat(cli)!: change manifest schema
~~~

The Conventional Commits check validates both the pull request title and all
commit messages. A pull request cannot be merged while this required check is
failing or pending.

## Pull Request Description

Describe:

- what changed and why;
- how the change was tested;
- whether documentation, scenarios, or release notes need updates;
- any compatibility or migration impact.

Keep pull requests focused. If a change spans repositories, explain the order
in which the pull requests should be merged.

## Validation Flow

Run the relevant local checks before opening a pull request. Depending on the
repository, these include Ruby tests, shell syntax checks, Terraform and
OpenTofu formatting and validation, TFLint, Checkov, and GitHub Actions
actionlint.

Public infrastructure checks run without cloud credentials and stop at
Terraform and OpenTofu plan. They generate and validate the manifest, render
the configuration, initialize providers, and verify both plans.

Real DigitalOcean apply tests use the same scenarios from the public
integration-tests repository and run through private-workflows. They are
reserved for release candidates and infrastructure changes. Never commit
tokens, state files, generated credentials, or private infrastructure data.

For reproducible integration checks, pin the CLI, provider modules, and
integration-tests repository to explicit tags or commits. Use main only when
intentionally testing unreleased changes.

## Scenario And Module Changes

Keep provider scenarios and their runner logic in integration-tests. Extend the
shared lifecycle and coverage metadata instead of duplicating workflows per
scenario. Use the cloud provider's native resource names and ensure resources
are isolated per workflow run.

When adding or changing a provider module, update its public plan coverage and
the corresponding private apply coverage where practical. Test both Terraform
and OpenTofu unless the change is specific to one tool.

## Releases

Release Please builds the shared release notes from Conventional Commits and
groups changes by category, with features before fixes. Do not use a release
type merely to describe CI or documentation work; choose the semantic impact
that applies to the user-facing project.

The release PR generated by Release Please is an automation exception to the
normal contribution-title rule. Source version files, tags, changelogs, and
release assets must remain aligned.

## Security

Do not disclose secrets, access tokens, state files, or private environment
details in issues, pull requests, logs, or generated artifacts. Report
security issues through the repository's security policy.
